# heel v1 design (enterprise, self-hosted)

## Intent

heel sits between AI agents and the systems they act on, and decides what each agent does with its tools:

- rules on the actual arguments of every call,
- hiding what an agent shouldn't read,
- approvals the agent can't answer itself,
- a pause switch,
- one place to see everything agents did.

The README describes the whole product. This document covers the first version.

v1 is for companies. Their agents act on employees' mail and calendars, and today that comes with per-tool switches at best and no view across agents. The companies pay for control. The funded players here (WorkOS Airlock, Keycard, Agent Auth) are closed and hosted. heel is open source and runs in the company's own cloud, so the company's email never leaves its infrastructure.

**Success:** a company on Google Workspace deploys heel, points its employees' agents at it instead of at Gmail and Calendar directly, and runs a week in record mode. It then reviews rules heel proposes, switches to enforce, and from then on its security team can answer "what did our agents do, and what did we stop?" from heel's dashboard.

## Goals

- **Google Workspace on both ends.** People sign in to heel with their company Google account, and groups come from the company's Google directory. Gmail and Calendar are the first integrations.
- **Employees' agents connect to heel as custom MCP connectors** instead of to Gmail and Calendar. Claude, ChatGPT and Grok all support this on business plans.
- **Rules in Cedar.** Organization rules sit above personal rules and can't be loosened. heel computes state facts (everyone in the thread, messages deleted this hour) and passes them to Cedar as context.
- **Three modes, switchable live per group:** record, shadow, enforce.
- **Rule suggestions** drawn from record-mode traffic.
- **Approvals** routed to the account's owner or a named approver, delivered by phone push with email as a backup.
- **Pause** for one person, one agent, one service, one group, or everyone.
- **Observability:**
  - an inventory of agents,
  - a live decision stream,
  - an event explorer,
  - the approvals queue,
  - SIEM export.
- **Calendar runs through the generic MCP proxy path,** proving heel works in front of someone else's MCP server.

## Non-goals for v1

These stay in the README and come later:

- the CLI path (`heel run`) and the HTTP API proxy;
- code mode;
- services beyond Gmail and Calendar;
- identity providers other than Google Workspace (Okta, Entra, SCIM);
- a hosted version run by us;
- model-based classification.

## Anti-goals

v1 fails, even if it technically works, if any of these hold:

- Any path lets a call through when heel can't decide: an error, a timeout, an invalid policy, or heel being down. heel fails closed.
- An agent can approve its own request, or a person can approve a request that an organization rule routes to someone else.
- A personal rule loosens an organization rule.
- An approved call runs twice, or runs after the agent gave up on it.
- A model makes any decision on a live call.
- Rollout is so noisy that a company turns heel off. That's why record mode, shadow mode and rule suggestions ship in v1.

## Constraints

- **It's self-hosted.** heel runs as one container plus Postgres in the company's cloud.
- **heel must still be reachable over public HTTPS.** Claude, ChatGPT and Grok call MCP connectors from their vendors' clouds, not from employees' machines.
- **The agent clients:**
  - Each one's custom connector flow does MCP OAuth discovery and dynamic client registration.
  - On business plans an admin usually provisions the connector first. Grok Business does this in console.x.ai, and Claude Team and Enterprise owners add org connectors.
  - The setup docs cover all three.
- **The Google OAuth client:**
  - The company creates its own in its Google Cloud project, as an **Internal** app.
  - Internal apps in a Workspace org skip Google's verification for restricted Gmail scopes, and they don't get the 7-day token expiry.
  - Each employee consents for their own account. heel does not use domain-wide delegation, so it never holds access to someone who hasn't connected.
- **Groups need the Directory API.** Reading Workspace groups needs a service account the Workspace admin authorizes with a read-only groups scope. That's the only org-wide grant heel asks for.
- **Google's Calendar MCP server** (`https://calendarmcp.googleapis.com/mcp/v1`) is in developer preview. It needs the Calendar MCP API enabled.
- **Google's Gmail MCP server can't send or delete,** so Gmail uses heel's own tools on the Gmail API.
- **Stack:**
  - TypeScript on Bun, with the official MCP TypeScript SDK and Postgres.
  - Cedar through the official WebAssembly build (`@cedar-policy/cedar-wasm`).
  - Shipped as a Docker image, with a Railway template for trials.
  - Apache 2.0.

## Approaches

| Approach | What it is | Trade-off |
| --- | --- | --- |
| A. Proxy only | Proxy Google's MCP servers for both services | Gmail loses send and delete, the calls the rules exist for |
| B. Native tools only | heel implements Gmail and Calendar on Google's APIs | The generic proxy path stays unproven |
| **C. Proxy core plus native Gmail (picked)** | One decision pipeline in front of heel's own Gmail tools and Google's Calendar MCP server | Slightly more than B; proves both paths |

Other choices Avi made:

- **Cedar over heel's own YAML.** Enterprise familiarity, deny-always-wins semantics, and analyzable policies.
- **Self-hosted over hosted.** Mail stays in the company, and it's the clearest difference from the closed competitors.

## Architecture

```
agent client (Claude / ChatGPT / Grok, vendor cloud)
   │  Streamable HTTP + OAuth (token = person + agent)
   ▼
heel /mcp/gmail   /mcp/calendar
   ├─ identify: person, groups, agent
   ├─ pause check
   ├─ map tool → action + resource (built-in definitions)
   ├─ compute context (state lookups, counters)
   ├─ Cedar: org + personal policies → deny | ask | allow
   ├─ mode: record / shadow / enforce (per group)
   │     allow → upstream     deny → error     ask → pending → approver
   ├─ upstreams: native Gmail (Gmail API) | proxied Calendar MCP (Google)
   ├─ hide: Cedar check per returned message
   └─ event: every decision, to Postgres + live stream + export
```

### Identity

- **People** sign in to heel's web app with Google (OIDC, restricted to the company's domain). Groups sync from the Directory API every 15 minutes and on every sign-in.
- **Agents:**
  - heel is an MCP OAuth 2.1 authorization server with dynamic client registration and PKCE.
  - When an employee adds heel as a connector, the consent step signs them in with Google. The issued token is bound to `(person, agent client)`, and the agent's name comes from the registered client name ("Claude", "ChatGPT", "Grok").
  - Every call carries that token.
- **Accounts:**
  - v1 has one Google account per person, their own.
  - After consenting for the agent, the employee connects their Google account through a Google OAuth flow. heel stores the refresh token encrypted with AES-256-GCM, using a key from an environment variable or a KMS.
  - heel refuses to start without a valid key.

### Agents (builder-check calls)

- An agent is one OAuth client registration bound to one person: `Agent::"<registration id>"`, with that person as its parent. The same vendor used by two employees is two agents. An admin-provisioned org connector still results in a per-person token.
- The agent's vendor (`claude`, `chatgpt`, `grok`) is verified from the registered redirect URIs against a known list of vendor domains. Anything else is `unverified`. Policies can match the verified vendor attribute (`principal.vendor == "chatgpt"`), never the free-text client name. Admins can block unverified vendors with a forbid.

### Roles and visibility (builder-check calls)

- Admins are members of a Google group named in config (for example `heel-admins@company.com`). One bootstrap admin email in an environment variable covers first setup.
- Admins see every event's metadata: who, which agent, action, recipients, subject, decision. They never see email bodies unless body storage is turned on.
- Employees see their own agents' events, their pending approvals, and their personal policies.

### Tool surface

- **Two MCP endpoints:** `/mcp/gmail` and `/mcp/calendar`. The token says whose account.
- **Native Gmail tools:** `search_threads`, `get_thread`, `get_message`, `send_message`, `reply` (with a reply-all flag), `forward`, `create_draft`, `trash_messages`, and `modify_labels`.
- **Calendar tools are whatever Google's server lists.** Any tool without a built-in definition is denied unless a policy names it.
- **Both endpoints also list:**
  - `heel_run_approved(id)`, which runs an approved call with exactly the arguments the approver saw, so the agent doesn't have to resend identical arguments;
  - `heel_approval_status(id)`.

### Built-in definitions

These map each tool to a Cedar action and resource, and compute context.

| Cedar action | Tools | Context |
| --- | --- | --- |
| `Action::"email.read"` | search, get_thread, get_message |  |
| `Action::"email.send"` | send_message, reply, forward | `recipients` (set), `recipient_domains` (set), `all_in_thread` (bool), `thread_id` |
| `Action::"email.draft"` | create_draft | `recipients`, `recipient_domains` |
| `Action::"email.remove"` | trash_messages, and modify_labels removing INBOX | `items`, `items_this_hour`, `items_this_session` |
| `Action::"email.label"` | other modify_labels |  |
| `Action::"email.view"` | each message in a read result (used by hide) | `from`, `from_domain`, `subject`, `labels`, `looks_like` (set) |
| `Action::"calendar.read"` | list, search, get, suggest_time |  |
| `Action::"calendar.create"` | create_event | `attendees`, `attendee_domains`, `only_self` |
| `Action::"calendar.update"` | update_event | the above plus `existing_attendees`, `existing_attendee_domains` |
| `Action::"calendar.delete"` | delete_event | `existing_attendees`, `existing_attendee_domains` |
| `Action::"calendar.respond"` | respond_to_event |  |

- **The principal** is `Agent::"<id>"`, with parents `Person::"<email>"` and that person's `Group::"<group>"`s. Policies can target a person, a group, or a specific agent, such as only ChatGPT.
- **The resource** is `Account::"<email>"`, with an `owner` attribute.
- **The state lookups:**
  - `all_in_thread`: every recipient was on a message the account owner sent in that thread.
  - `existing_*`: fetched before deciding.
  - A failed lookup is a deny.
- **The counters:** `per hour` is per agent. `per session` uses the MCP session id. The spike decides whether session counts survive (see below).

### Policies

- **Two policy sets:**
  - **Organization** policies are edited by admins.
  - **Personal** policies are edited by each person, for their own principal only. The linter rejects a personal policy whose scope is anything other than `principal in Person::"<self>"`.
- **Decision rule:**
  - Any matching `forbid`: **deny**.
  - Otherwise, any matching `permit` annotated `@heel_ask`: **ask**.
  - Otherwise, any matching plain `permit`: **allow**.
  - No match: **deny**.

  Ask outranks allow, so an organization ask can't be loosened by a personal permit.

- **Approvers:** `@heel_ask("owner")` is the default and routes to the account's owner. `@heel_ask("group:security")` routes to a group. `@heel_no_standing` on an ask policy forbids "allow for N days" approvals.
- **Standing approvals:**
  - An approver can approve once, or for N days.
  - A standing approval covers the same action, account and recipients or attendees, and turns that ask into an allow.
  - It never overrides a forbid, and it's dropped when the policy that asked changes.
- **The linter:**
  - It runs on every save and in CI. It uses Cedar's validator against heel's schema, plus heel's own checks: a session-count condition with no hourly one, an unknown context field, or a personal policy outside its scope.
  - Errors carry policy id, line, column and a suggested fix.
  - An invalid save is rejected, and the previous version stays live.
- **Storage:**
  - Policies are stored in Postgres with full version history, and every change is an event.
  - They're edited in the dashboard, with inline linting, and can be exported and imported as `.cedar` files for teams that keep them in git.
- **Starter policies** ship as `examples/org-default.cedar`:
  - Reads are allowed.
  - Sends to recipients all inside the company domain are allowed.
  - Sends to anyone outside ask the owner.
  - Removing more than 20 messages in a session or 100 in an hour asks.
  - Calendar invites with outside attendees ask.
  - Password resets and login codes are hidden.

### Hide

- **Hide is a Cedar check per returned message,** using `Action::"email.view"`. A `forbid` hides that message.
- **Hidden messages are removed** and replaced by one placeholder per call with a count. Acting on a hidden message by id is denied.
- **`looks_like` is computed by a built-in, readable pattern list,** with no model:
  - sender addresses,
  - subject phrases,
  - code and reset-link formats.

  The list lives in the repo so anyone can add to it. Record and shadow modes log what the list would hide, so a company sees what it catches on real mail before enforcing.

### Modes and rollout

- **The modes:**
  - **record:** allow everything and log everything.
  - **shadow:** evaluate, log what would have happened, and allow.
  - **enforce.**
- **Modes are set per group,** with an organization default, and take effect on the next call with no restart.
- **Pause and fail-closed apply in every mode.** In record and shadow, no approvals or notifications are created.
- **When a person is in several groups with different modes, the strictest wins:** enforce, then shadow, then record. Before an admin switches a group's mode, the dashboard shows how many people that changes. (Builder-check call.)
- **What still denies in record and shadow modes:** pause, an invalid or missing token, and a failure to decrypt a provider token. A failed state lookup or a Cedar error is logged as a would-deny and the call is allowed, because nothing is enforced in those modes by choice. Enforce mode denies on all of them. (Builder-check call.)
- **Rule suggestions:** after record or shadow mode, heel groups observed calls by group, action and shape (recipient domains, counts) and drafts Cedar policies. An admin reviews and saves them. Suggestions are only text until saved.

### Approvals

- **Pending:**
  - An ask returns an MCP tool result right away: "pending approval, id apr_..., the approver has been notified, call `heel_run_approved` with this id once approved".
  - A retry with the same hash of agent, action, account and arguments joins the same request.
- **Notify:**
  - heel sends web push to the approver's subscribed devices. The approval page is an installable web app.
  - If no one decides within 2 minutes, heel emails the link.
  - Notifications show the action and account, never the arguments.
- **Approve:**
  - The approver signs in with Google, and the sign-in must be recent.
  - The page shows the agent, the person, the account, the action, the full arguments and the policy that asked.
  - An approver can't approve their own agent's request when the policy routes it to a group.
- **Running an approved call (builder-check calls):**
  - Only the same `(person, agent)` that made the request can run it.
  - heel re-runs the full pipeline with the approved arguments. The approval satisfies the ask, but a forbid added since then, a pause, or a group change that removes the matching permit still blocks it.
  - If a client never comes back, by retrying or calling `heel_run_approved`, the approved call never runs. heel never runs a call on its own. The spike records which clients come back, and the setup docs list them.
- **Execute:**
  - The call runs once, claimed in the same transaction that marks the approval used.
  - Requests expire after 24 hours.

### Pause

Admins can pause a person, an agent, a service, a group, or everyone. A person can pause their own agents. Every call during a pause gets a "paused" error, and pending approvals can't be approved. Pause state is read on every call, never cached.

### Observability

- **Events:**
  - Every call produces one event: who, which agent, the action, the account, normalized arguments (email bodies are not stored by default, and storing them is a setting), the decision, the mode, the matching policies, the approval, the upstream result and the duration.
  - Policy changes, mode changes, pauses and sign-ins are events too.
  - The event log is append-only.
- **Dashboard views:**
  - **Overview:** calls, blocks, asks and approvals over time, plus top agents and top blocked actions.
  - **Agents:** an inventory of every person and agent pair, with last seen, call counts and mode.
  - **Live stream:** server-sent events with filters.
  - **Event explorer:** search by person, agent, action, decision, policy and time.
  - **Approvals:** pending, decided, expired.
  - **Policies:** the editor, the linter, history, and suggestions.
- **Export:**
  - JSON lines to stdout, which any log shipper picks up.
  - An OpenTelemetry logs exporter.
  - Each SIEM needs no connector of its own in v1.
- **Retention:** 90 days by default, configurable.

### Failure behavior

Any exception while deciding, including a Cedar evaluation error, is a deny. A failed state lookup is a deny. An unreachable upstream returns an error. A policy that fails linting is never activated.

## The first step: a spike against real clients

Before building counters and approvals, connect a bare heel endpoint (OAuth plus one echo tool) to Claude, ChatGPT and Grok, and record:

- how each handles registration and token refresh,
- whether `Mcp-Session-Id` lasts a conversation,
- what each does with a "pending approval" result,
- whether each will call `heel_run_approved`.

If no client keeps sessions, session counters are dropped from v1 and only hourly counts remain.

## What's left to the builder

- Libraries inside the stack: the HTTP framework, the Postgres client and migrations, web push, OpenTelemetry.
- The JSON shapes of the native Gmail tools.
- How the dashboard looks, as long as approvals show the full arguments.
- The initial `looks_like` pattern list.
- The rule suggestion algorithm, as long as the output is reviewable Cedar.
- Tests. At minimum: each README incident replayed against the starter policies; organization forbid beating personal permit; ask beating permit; pending, approve and run exactly once under concurrent calls; and fail-closed on every injected error.
